# YouTube ナビゲーションリファレンス

YouTube がページ遷移（ナビゲーション）をどのように行うかを記述する。拡張実装とテストの双方で必要になる共有リファレンスであり、テスト側の待機ルールは `AGENTS.md` にある。

この文書が記述するのは YouTube であり、拡張機能ではない。拡張機能自体の契約は
`SPEC.md` である。YouTube は予告なくこの挙動を変更する。テストがこの文書で説明されていない仕方で失敗したときは、修正とともにこの文書も更新する。

## ナビゲーションシグナルと各々が証明すること

| シグナル                                                          | 何か                                                    | 何を証明するか                                  | 何を証明しないか                                                                      |
| ----------------------------------------------------------------- | ------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------- |
| `domcontentloaded`                                                | HTML document のパース完了                              | document が存在する                             | SPA が何かをレンダリング・ルーティングしたこと                                        |
| ナビゲーション開始（`yt-navigate-start` / `state-navigatestart`） | ルーターが遷移を受け付けた                              | 遷移が始まった                                  | 遷移が完了したこと、着地ルートがどこか                                                |
| ナビゲーション終了（`yt-navigate-finish` / `state-navigateend`）  | ルーターが遷移を完了した                                | 発火時に記録された URL のルートで遷移が終わった | 追従 UI（グリッド・チップ）のレンダリング完了、追加の遷移が始まっていないこと         |
| URL 変化                                                          | `pushState`（soft）または document 読み込み（hard）     | 可視ルートが動いた                              | soft 変化について: ルーターの内部状態が準備済みであること（下記ドロップ時間帯を参照） |
| sort 応答 + グリッド入れ替え                                      | その sort 自身の `/youtubei/v1/browse` 応答が描画された | クリックした sort が適用された（下記）          | ナビゲーションについての何も — sort はナビゲーションではない                          |

ハードナビゲーション（完全なページ読み込み）: ルーターは初期読み込みの完了後、ナビゲーション終了を一度だけ発火する。開始イベントは先行しない。ソフト（アプリ内）ナビゲーション: 開始、次に終了。コミット済み document の差し替え（ハードナビゲーション、リダイレクト）は、リスナー・フラグ・データを含むページ状態をすべて初期化する。

## ソフトナビゲーションの仕組み

アプリ内アンカーのクリックはブラウザナビゲーションを一切行わない。ルーターは次のステップで処理する:

| ステップ | 何が起こるか                                                                                                     |
| -------- | ---------------------------------------------------------------------------------------------------------------- |
| 1        | document レベルのルーターリスナーがクリックを捕捉し、アンカーに対して `preventDefault()` を呼び出す              |
| 2        | ナビゲーション開始イベントが発火し、ページデータがリクエストされる（`/youtubei/v1/browse` と関連エンドポイント） |
| 3        | SPA がページを再レンダリングし、`pushState` で URL を更新する                                                    |
| 4        | ナビゲーション終了イベントが発火する                                                                             |

DOM はルーターの内部状態の準備より先にレンダリングされうる。この時間帯のアプリ内アンカーへのクリックは、ステップ 1 と 2 の間で静かにドロップされることがある — ナビゲーションイベントは発火せず URL も動かない。したがって「クリックが飲み込まれた」ことは、すべての開始シグナルの不在からのみ証明でき、経過時間だけからは決して証明できない。同一アンカーの再クリックでもこのドロップは起こりうる。

モバイル YouTube は別の実装であり、イベント名も異なる。拡張機能は
`src/entrypoints/play-all-button.content/youtube-hooks.ts` でそれらを対応付ける:

| スコープ | ナビゲーション開始    | ナビゲーション終了   |
| -------- | --------------------- | -------------------- |
| Desktop  | `yt-navigate-start`   | `yt-navigate-finish` |
| Mobile   | `state-navigatestart` | `state-navigateend`  |

モバイルで `www.youtube.com` へハードナビゲーションすると、`m.youtube.com`
へ単一のコミット済み document としてリダイレクトされ、その初期読み込みで
モバイルのナビゲーション終了イベントが一度発火する（一部の読み込みでは 2 回
発火も観測されている）。m ルートからの `m.youtube.com/#searching` のような
ハッシュのみの URL 変化は同じ document のまま扱われ、ナビゲーションイベント
は発火しない。これは検索 UI を開く操作であり、ルート遷移ではない。

### 検索結果 URL

結果ページの URL は `…/results?search_query=<query>` だが、追加のクエリ
パラメータがその前後に来ることがある（保存されたモバイルトレースでは
`/results?sp=mAEA&search_query=%40Apple` を観測）。パラメータの並びと追加
パラメータは契約ではない。位置によるパターンではなく、パースした pathname
とデコード済みの `search_query` 値を検証すること。追加パラメータを付与する
要因は不明である（モバイル実行のすべてに出現したわけではない）。

## sort 切り替えはナビゲーションではない

sort チップ（Latest / Popular / Oldest）のクリックは SPA ルーターを経由しない。
ナビゲーションイベントは発火せず、URL のクエリも変化しない。代わりにページは
その場で更新される:

| ステップ | 何が起こるか                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | チップの `aria-selected` がすぐに反転する（mobile では選択済みチップが一度 false に戻ってから true に戻ることがある）                                                                                                                                                                                                                                                                                                                                                                                                  |
| 2        | クリックはページコンテキストから `/youtubei/v1/browse` をちょうど 1 件リクエストし（fetch）、そのボディはクリックしたチップの継続トークン（`chip-view-model` の `data.tapCommand.innertubeCommand.continuationCommand.token`）を伴う。応答は次ページ用の継続トークンを伴う。選択済みチップを含む 3 チップすべてがトークンを持つ。mobile ではチップの描画後に data が付与されることがある。リクエストボディはクライアントが対応している場合 gzip 圧縮されるため、ボディを観測するテストはパース前にデコードが必要である |
| 3        | クリック直後、応答の到着前に、グリッドが古い sort の動画を再レンダリングすることがある: 先頭動画ノードが同一 href の別ノードに置き換えられる                                                                                                                                                                                                                                                                                                                                                                           |
| 4        | browse 応答が着き、それでページが再レンダリングされる: 動画グリッドが新しい sort の動画に DOM ごと入れ替わり、desktop では同じタイミングでチップバーも再構築されて、その中に anchor されたノード（拡張機能の UI を含む）が detach される                                                                                                                                                                                                                                                                               |
| 5        | 選択済みチップの再クリックでも browse リクエストが再発行され、グリッドは入れ替わる。no-op ではなく、置換後のノードが同じ href を保つこともある                                                                                                                                                                                                                                                                                                                                                                         |

ステップ 3 のため、「先頭動画ノードが置き換えられた」だけではクリックした sort
が適用されたことの証明にならず、無関係な browse 応答と再レンダリングの組み
合わせも何も証明しない。因果ゲートは順序ではなく同一性と適用済み内容である:
リクエストボディがクリックしたチップの継続トークンを伴う応答が到着済みであり、
グリッドの可視動画 id の順序がその応答の内容と一致すること。その上に重なる
有界の quiet window はグリッドが落ち着くのを待つテストのヒューリスティック
であって、YouTube の保証ではない。レンダリングと応答到着の順序は意図的に
前提としない。レンダリングが自分の応答に先行しうるかは未解決である。チップ
トークンや一致する応答を観測できない場合はフェイルクローズドする。拡張機能の
Play All ボタンは別経路で解決され、グリッドより遅れることがある（Oldest は
ネットワーク裏付けのプレイリスト）。

まれに、sort クリックが `aria-selected` を反転させるが browse リクエストを
一切発行せず、グリッドも変化しないことがある（1 台のマシンで短時間に多数の
新生ヘッドレスコンテキストを起動した系列で繰り返し観測。e2e 相当セッション
では未観測）。トリガーは不明である。このようなセッションは、置換だけを待つ
のではなくトークン一致でフェイルクローズドするもう 1 つの根拠である。

## チャンネルタブ

チャンネルページのタブは `yt-tab-shape` 要素として描画される（desktop・mobile
web とも）。ローカライズされた `tab-title` 属性（ホーム/動画/ショート/ライブな
ど）と `aria-selected` は持つが、href は持たない。`yt-tab-shape` には
`tab-identifier` シグナルプロパティが存在するが、観測したすべてのケースで
未設定だった。観測された並びは Home, Videos, Shorts, Live, Playlists,
（Search）で、Live タブのクリックは `/@channel/streams` へ遷移する。ラベルは
ローカライズされ、並びも契約ではないが、タブの同一性はページのデータモデル
から機械可読である: タブごとに 1 つの `tabRenderer` を持ち、その
`endpoint.commandMetadata.webCommandMetadata.url` がカテゴリルートを保持する
（例: `/@Apple/videos`）。所在地は `contents.twoColumnBrowseResultsRenderer.tabs`
（desktop）/ `contents.singleColumnBrowseResultsRenderer.tabs`（mobile）である。

そのモデルをどのオブジェクトが持つかは、ページへの到達方法による:

- ハードロード後は `ytInitialData` が現在ページのモデルである。
- ソフト到着後は、`ytInitialData` は初期ハードロード時のモデルのままであり、
  document 内に複数の `ytd-browse`/`ytm-browse` 要素が同時に存在しうる —
  以前にルーティングされたページの古い非表示要素（観測例: 非表示の home
  browse が document の先頭に残存）と、現在ページの browse 要素（その
  `.data` が現在のモデルを保持する）。first-match の読み取りはよそページの
  モデルを解決するため、現在のモデルは内容で特定する必要がある: 期待する
  ルートに一致するタブ endpoint である。現在の browse の data は着地後に
  付与されることもあるため、配列形状のモデルを待つのではなく、一致する
  endpoint を待つ必要がある。
- いずれも `.data.tabs` を直接は持たず、タブは
  `.data.contents.*BrowseResultsRenderer.tabs` の下にある
  （`yt-tab-shape` 自身の `.data` は null である）。

モデルのタブ並びは、観測したすべてのケースで `yt-tab-shape` の DOM 順と一致
した。この前提が破れた場合の最終的な因果チェックとして、クリックが着地した
URL を引き続き使う。

## 観測範囲と未知点

desktop・mobile web の Chromium と desktop の Firefox で、ヘッドレスの
プローブセッションとテスト用拡張機能をロードした e2e 相当セッション、
日本語・英語 UI、少数のチャンネル（@Apple 等）で観測した。生のプローブログ
と詳細な実験記録はこのファイルではなく、このリポジトリのテスト作業記録に
ある。未知点:

- チップトークンとリクエストボディの一致が長期的・チャンネル横断的に成り立つか。
- 上記のノーリクエスト sort セッションのトリガー。
- グリッドのレンダリングが自分の sort 応答に先行しうるか（順序は前提にしていない）。
- 選択済み _カテゴリ_ タブの再クリックが navigation-end を再発火するかどうか。
- チャンネル間でタブ並びがどの程度変化するか、タブモデルの並びが
  `yt-tab-shape` の DOM 順から乖離しうるか（1:1 を仮定。乖離があれば
  誤タブクリックとして現れ、着地 URL の待機で後から検出される）。
- 検索結果 URL に追加パラメータを付与する要因と、その出現の安定性。
- 適用済み内容チェックは、グリッドの先頭の可視動画 id が応答の走査順で
  先頭の `videoId` 値と一致することを仮定する。先頭項目が描画されない
  応答（フィルタ・非公開など）はフェイルクローズドとなる。
